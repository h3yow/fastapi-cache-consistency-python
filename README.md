# fastapi-cache-consistency-python

在读接口前加一层本地可复现的查询缓存，挡住重复的底层查询。多个业务线共用同一份缓存时，
失败/降级/恢复**按键互相隔离**，缓存带**容量上限与 LRU 淘汰**，降级时对外只给**固定可枚举类别**。

## 结构

- `cache_layer/cache.py` — 缓存核心：`QueryCache`、单键状态机 `CircuitBreaker`、`CacheResult`、
  对外降级类别 `DegradeReason`、来源 `Source`。
- `cache_layer/backend.py` — `FakeBackend`：可编程延迟/故障的底层存储模拟，用于本地复现超时、连接失败与恢复。
- `main.py` — FastAPI 读接口 `GET /items/{item_id}`，演示命中、回源与降级。
- `tests/test_cache.py` — 12 个场景共 14 条用例（场景见下文“测试覆盖”）。

## 读写语义

`QueryCache.get(key)` 返回 `CacheResult(value, source, reason)`，`source` 可区分四种情况：

| source | 含义 |
|---|---|
| `hit` | 缓存命中（含空结果命中），不访问底层 |
| `backend` | 本次请求真正触发了回源，并写入缓存 |
| `joined` | 并发等待方，复用同一次回源结果 |
| `degraded` | 该键底层不可用或熔断中，`reason` 字段给出**固定类别** |

- 命中时绝不访问底层存储；未命中时回源并写入。
- 同一键的并发请求合并为一次真实回源（单飞），等待方拿到同一次结果。
- 回源失败**不写入缓存**，只返回降级结果，异常不向调用方透出。

## 按键隔离的适用范围

熔断状态（失败计数、断开时刻、冷却、半开试探）**按缓存键各存一份**：

- 某个键连续失败达到 `failure_threshold` 后，只封这一个键；其它键该命中命中、该回源回源。
- 一个键处于降级/冷却中，不会让其它未失败的键也被直接拒绝；其它键未缓存时照样回源。
- 冷却（`cooldown` 秒）过去后，**每个键各自半开试探**：成功只闭合自己，失败只重开自己，
  不会因为“还有键没恢复”而把已恢复的键继续封着。
- 多键同一时刻一起失败或一起恢复，各自用独立计数器和独立断开时刻判定，互不串状态。

适用范围说明：隔离粒度是“同一个 `QueryCache` 实例内的缓存键”。熔断只针对**回源失败**
（异常/超时）；缓存数据本身（命中、过期、淘汰）不涉及熔断。

> 实现细节：熔断器条目在某键**首次失败**时创建，在该键**试探成功恢复**时移除；处于失败/熔断中的
> 键即使缓存数据被 LRU 淘汰，其失败计数仍保留到冷却后的那次试探出结果为止（避免淘汰缓存就
> 等于绕过熔断保护）。熔断状态对象很小（计数 + 断开时刻），与缓存数据条目分开存放。

## 容量上限与淘汰规则

构造参数 `max_capacity`（正整数，默认 `None` 表示不限容量；传非正数会抛 `ValueError`）：

1. 缓存按 **LRU（最久未用）** 维护顺序：命中（含空结果命中）与新写入都会把该键刷新为最近使用。
2. 写入导致条目数超过上限时，从**最久未用**的键开始淘汰，直到条目数回到上限。
3. 被淘汰的键下次访问按未命中处理：**正常重新回源**，拿底层最新值，不会返回过期旧值，也不会报错；
   被淘汰的空结果再访问时与第一次完全一样——重新回源并重新缓存为空结果。
4. 淘汰只删除缓存数据（`_store`），**不碰在途回源注册表**（`_inflight`）：淘汰窗口内同一键的
   并发请求依旧合并到同一次回源，等待方拿到同一次结果，不会被冲散成多次回源。
5. 空结果同样占用一个容量条目。

## 对外降级类别（`DegradeReason`）

`CacheResult.reason` 只有以下三个固定枚举值，调用方据此区分故障形态：

| reason | 含义 | 此时是否访问底层 |
|---|---|---|
| `timeout` | 该键回源超过 `load_timeout` 秒 | 访问了，但超时 |
| `unavailable` | 连不上 / 底层调用抛异常 | 访问了，但失败 |
| `circuit_open` | 该键连续失败处于熔断冷却期，被直接挡住 | **不访问** |

- **信息边界**：`CacheResult` 和 HTTP 503 响应里只有上面这些固定字符串，
  **不包含任何底层异常的类型名、异常消息或调用栈**（例如不会出现 `BackendUnavailableError`）。
- 具体异常类型名、消息、失败次数、冷却剩余时间等**判定依据只写服务内部日志**
  （logger 名 `cache_layer`，`WARNING` 级，含 `key/reason/basis/failures/cooldown/detail`）。
- 半开试探若仍失败，该键以当前时刻重新计时冷却；试探成功则该键立即闭合，恢复正常回源与写缓存。

## 测试覆盖

`tests/test_cache.py` 覆盖以下场景，每条用例的 INFO 日志都会打印键、来源、类别、耗时与判定依据：

1. 并发回源合并（单飞）；2. TTL 过期重新回源；3. 空结果缓存；4. 降级与自动恢复；
5. 失败不写缓存；6. 按键隔离（降级中互不阻挡 + 恢复互不影响）；
7. LRU 容量淘汰；8. 淘汰后重新回源（含空结果重新缓存）；
9. 淘汰窗口内并发仍合并；10. 降级类别可区分且响应不泄露底层细节（细节只在内部日志）；
11. 超时单独归类；12. 多键同时失败/同时恢复不串状态。

## 本地验证

```bash
uv run pytest -q --log-cli-level=INFO   # 日志打印每个场景的键、来源、类别、耗时、判定依据
uv run python main.py                   # 启动服务后访问 GET /items/1
```

- 正常请求返回 `source` 为 `hit` / `backend` / `joined`；降级时 HTTP 503，
  响应体 `reason` 只会是 `timeout` / `unavailable` / `circuit_open` 之一。
- 可构造观察：把 `main.py` 的 `max_capacity` 调小观察 LRU；
  `FakeBackend(down=True)` 观察某键熔断不影响其它键；`FakeBackend(latency=...)` 超过
  `load_timeout` 观察 `timeout` 类别。
